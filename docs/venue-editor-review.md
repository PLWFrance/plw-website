# Venue editor review — Task 3

## Supported editor organisation

Reviewed Pages CMS 2.1.8's current upstream schema and select implementation on 5 November 2026. Sources: [config schema](https://github.com/hunvreus/pagescms/blob/6f4e860a35d934406580287e7042e5e111e207a1/lib/config-schema.ts), [registry](https://github.com/hunvreus/pagescms/blob/6f4e860a35d934406580287e7042e5e111e207a1/fields/registry.ts), [select editor](https://github.com/hunvreus/pagescms/blob/6f4e860a35d934406580287e7042e5e111e207a1/fields/core/select/edit-component.tsx). The upstream repository has moved from `pages-cms/pages-cms` to `hunvreus/pagescms`. Hosted deployment version is not exposed by this repository; verify rendering in the hosted app.

`content.type: group` groups navigation entries, not fields within a venue. Ordinary object fields nest saved data; they do not act as layout-only wrappers. The schema has no field tabs, fieldset, or ordinary-object `collapsible` property. Moving flat fields into nested section objects would require a content migration and template changes, so it is deliberately avoided. Seven numbered first-field labels, logical ordering, concise help and collapsed repeated object items provide the simplest supported alternative. SEO remains an optional ordinary object at the end; it cannot be made collapsible with a supported layout flag. YAML comments document the section boundaries for maintainers but do not render headings.

`list.collapsible` supports collapsed entries and summary templates. Galleries use alt text, key information uses its heading, and offers use their title. `hidden: true` is supported on fields; the existing `fictional` flag stays in the model, with its safe default and merge behaviour preserved. `settings.config: false` hides the configuration editor. Neither is access control. Placeholder switches remain visible because they convey editorial facts, rather than being purely development controls. All record paths, body format, image paths, field names, draft filtering and site templates are unchanged.

## Classification catalogue and WordPress handover

`src/data/venue-features.json` is the single maintained catalogue. It has editorial categories for accommodation, facilities, activities, accessibility and wedding arrangements, with no claimed WordPress hierarchy. Only the existing four known choices are seeded. Empty categories are intentional: the actual terms have not been supplied. `amenities` remains a multiple-selection string array, so old records need no migration. Facilities free text and all quantitative/ceremony fields remain available.

Sarah searches the one multi-select by category/name and selects all confirmed features. Group labels are ordinary supported select labels (`Facilities / Parking`), not invented nested select configuration. The website continues displaying saved values with its existing design. Keep explanations, restrictions and qualified accessibility claims in key information/accommodation details; a feature is not a guarantee. Do not use absent selections to infer “no”.

Developer import procedure, once an authorised export is supplied:

1. Obtain taxonomy machine names and labels; every term's ID, exact label, slug, parent ID, description, ordering and active/retired status. Include custom taxonomies, relevant ACF/meta field definitions and allowed values if classifications live outside taxonomies. Obtain venue-to-term relationships keyed by stable WordPress venue ID and URL/slug, and examples of actual stored values, including unknown/false states. No credentials are needed in this repository.
2. Have Sarah approve a mapping from those terms/hierarchy into the editorial categories. Preserve source IDs in each feature's optional `wordpress: {taxonomy, termId, slug}` metadata. Resolve duplicate names, synonyms, punctuation/encoding, parent/child semantics and accessibility qualifications explicitly. The format supports one source term per feature; keep any many-to-one alias map in the reviewed import material, rather than discarding source identity. Do not silently merge terms.
3. Append approved features with a unique persistent `value`, editor `label` and category. The value is also displayed on the current website, so choose human-readable exact approved wording. Preserve all existing values, particularly `Swimming pool`, `Parking`, `Wi-Fi`, `Step-free access`. Match equivalent source terms to these values where verified. Change labels/categories freely; renaming/deleting saved values needs a separate migration. Retain retired choices until references are audited and Sarah approves a replacement strategy.
4. Run `npm run sync:features -- --write`, review `.pages.yml`, then run validation, tests and build. The default `npm run sync:features` checks for drift without writing. Astro reads allowed values from the catalogue; content validation checks the CMS options match, validates category/value uniqueness and rejects unknown selections. The generator changes only the feature choices, not venue records.
5. Review the expanded selector with Sarah before importing any venue assignments. Import venue content only in a separately authorised migration. Keep a source export and mapping so relationships and term identity can be reconciled. No WordPress access, live migration or invented terms are included here.

The catalogue is developer-maintained to avoid exposing structural taxonomy administration in Sarah's day-to-day venue form. A new confirmed feature is one catalogue entry plus the sync command, not parallel edits to CMS and validation enums. A large taxonomy may eventually merit a reference collection, but that adds editing and referential-integrity overhead; start with the supported searchable selector.

## Validation and manual acceptance

The script verifies Git blob hashes, uses upstream's registered field types and changes only module imports for local execution through `zod/v3`. Normal production builds do not fetch remote schemas.
